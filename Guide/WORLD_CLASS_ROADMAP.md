# Sura World-Class Positioning

> This file is a machine-checked feature-evidence inventory: `tools/sura_goal_audit.ps1`
> greps it for exact evidence strings, so entries here are data, not prose to trim.
> The human-readable plan lives in [../ROADMAP.md](../ROADMAP.md).

Sura's practical target is:

> A fast Python-like scripting language for games, automation, and AI agents that can embed into native apps like Lua while keeping a small, inspectable runtime.

## Pillars

- Easier than Python for small scripts: concise assignment, built-in JSON/schema/HTTP/filesystem/testing/logging.
- Embeddable like Lua: the C ABI surface lives in `sura_ffi.hpp`, `surapkg embed` scaffolds Windows/Linux/macOS native C++ host apps with PowerShell and CMake build files plus JSON scaffold reports, the versioned plugin ABI lives in `sura_plugin.h`, and the package bindgen can emit Sura stubs plus numeric/string `#define`, enum constants, and supported `typedef`/`using` aliases from C/C++ C-ABI headers.
- Fast enough for hot scripts: interpreter, bytecode compile/load, hardened v5 keyed/licensed/expiring randomized inspection-locked and tamper-checked protected source-free release packages with closed-source build enforcement, schema-versioned raw-source/secret leak reports plus `next_actions` remediation guidance, `protect-verify` CI evidence gates, obfuscated stripped protected launcher exe generation, Win64 x64 partial native JIT, Linux x86-64 exception-free straight-line System V baseline, and little-endian Windows/Linux/macOS ARM64 exception-free straight-line AAPCS64 baseline for constants, moves, proven-numeric addition/subtraction/multiplication/unary negation/six comparisons and division by a proven nonzero divisor with register-VM fallback, package-level JSON/Markdown benchmark reports with optional Python reference comparisons, C++ native performance baseline evidence, benchmark dashboard with Markdown summaries, benchmark regression and required-coverage gates, release evidence gates, and AOT bytecode launcher.
- AI/automation native: JSON-schema-style validation with `schema_validate`/`schema_errors`, safe JSON parsing with `json_try_parse`/`json.try_parse`, Sura-schema-to-JSON-Schema conversion with `schema_to_json_schema`, JSON path lookup/existence/set/delete helpers with `json_path`/`json_has_path`/`json_set_path`/`json_delete_path`, JSON Merge Patch updates with `json_merge_patch`, JSON-path collection helpers (`pluck`, `count_by`, `group_by`, `sort_by`), dictionary keys/values/items/merge/pick/omit helpers, array range/chunk/zip/repeat helpers, array-backed set union/intersection/difference/subset helpers, `template_render` for JSON/API payload templating, source-aware RAG prep helpers (`rag_sources`, `rag_prepare`), dedicated `tool <name> { ... }` calls, typed tool specs/schemas, field-constrained and approval-gated tool allow/policy checks plus JSONL audit logs for `http_get`, spec-based `http_request`, and shell tools, signed package-level `sura.tools.json` policies, token/env/command/interactive approvals plus JSON request/response file approval bridges for editor and embedded UIs, observable async command and async HTTP tasks, stream batching/counting/joining, Python bridge, HTTP helpers, vectors including 3D vector interpolation/projection/reflection/angle/4x4 transform helpers plus `graphics3d` mesh/camera helpers, tensors, OpenAI-compatible tool schema/request helpers, structured-output LLM request helpers/tool-run loops, prebuilt LLM request posting via `llm_chat_request`, LLM text/JSON extraction plus cost/budget checks, serialization, and source-grounded `surapkg agent` project scaffolding that uses namespaced `json`/`fs`/`rag`/`llm`/`tool` modules with a local `knowledge/` RAG corpus plus JSON scaffold reports.
- Embedded approval UI coverage: `SURA_TOOL_APPROVAL_REQUEST_FILE`/`SURA_TOOL_APPROVAL_RESPONSE_FILE` provide a UTF-8 JSON request/response bridge for editor and embedded UIs, and `tools/sura_tool_approval_smoke.ps1` verifies both allow and deny decisions through that bridge.
- Independent by default: Python/JS/C interop is a bridge to existing libraries and benchmarks, not a Python-to-Sura source translator or migration path. New Sura projects should be written in Sura first.
- Native neural-network training and autograd: resident CUDA supports real 2-byte f16/bf16 visible storage, typed cuBLAS/PTX matmul with f32 output/gradient, f32 master-weight SGD/Adam, loss scaling, checkpoint v3 exact CUDA leaf resume, and deterministic f32 causal-attention recomputation without an O(T²) backward workspace. The broader resident graph—transpose, embedding, causal attention, sparse CE, GELU/LayerNorm and reductions—remains f32-only. Tests 31 and 44–52 verify attention dispatch/precision, compute-only autocast, actual typed storage, master optimizers, loss scaling and restart continuity. Published RTX 4060 benchmarks still show PyTorch faster. Low activation/output, fast mixed backward, profiler-verified Tensor Core coverage, shared-memory tiled/low-precision FlashAttention, general broadcasting, batched-right matmul, CUDA token/target input, dense softmax/cross-entropy and NCCL remain absent.

- Transformer resource and recovery controls: `autograd.limits()` and `cuda_stats()` expose host/device limits and typed-storage counters. Checkpoint v3 stores CUDA visible weights plus f32 master, SGD velocity or Adam moments/metadata; `{optimizer: true, device: "cuda"}` restores an optimizer-ready leaf exactly, `{optimizer: false}` restores visible weights only, and v1/v2 remain readable. Tests 18, 31 and 51 cover CPU/CUDA continuity and corruption rejection.
- Sura 1.11.1 data and scale boundary: `tokenizer.byte` is a lossless raw UTF-8 byte tokenizer and `tokenizer.train_bpe` deterministically learns bounded byte-level BPE vocabularies (1 MiB corpus, vocabulary up to 4096, 64 MiB-token work budget). BPE encode/decode, versioned checksummed save/load, and chunk-boundary-preserving dataset packing work, but normalization and external tokenizer formats do not. `dataset` writes versioned uint32 shards and reads batches through seek I/O, without mmap or prefetch. `autograd.all_reduce_gradients` synchronously sums/averages CPU `float64` gradients through checksummed shared-filesystem rank files, not NCCL. A process may select a GPU before startup with `SURA_CUDA_DEVICE`, enabling process-per-device experiments, but resident CUDA gradients are rejected by the file all-reduce backend and no GPU collective exists.
- Sura 1.11.1 model interoperability: native standard Safetensors preserves all four storage dtypes; `tools/sura_torch_bridge.py` explicitly converts legacy PyTorch state dicts through Safetensors; ONNX APIs read/write typed initializers and `autograd.run_onnx` executes a bounded CPU IR 3–10/opset 7–18 subset (`Identity`, arithmetic, `Neg`, `MatMul`, activations, `Gemm`, full-permutation `Transpose`, `Flatten`, bounded raw-data INT64-shape `Reshape`, last-axis `Softmax`). Arbitrary graphs, Conv, dynamic shapes/control flow, external data and GPU execution remain unsupported.
